# 0026 事务的加锁顺序

- 状态：已接受（2026-10-30）；由 [0027](0027-decide-under-lock.md) 补充（加锁之后再判断；角色、删号、设置也纳入加锁顺序）
- 相关：ADR 0017、0020；提交 338ee51、15b690d

## 背景
CI 的 MySQL 测试两次因为死锁失败（公告投递；举报、建角色、上传、收藏），每次只修了出问题的那一处。M3 收尾后对全部事务做了一遍检查，又发现两个在 PostgreSQL 上同样会发生的死锁：

- 两个人同时收藏对方的材质：收藏要改自己的积分和上传者的奖励，两个事务以相反的顺序锁这两个用户。
- 两位管理员同时处理同一材质的两条举报：各自先锁住自己的举报，再去结案对方的那条。

根源相同：没有统一的加锁顺序。另外两种只在 MySQL 上出现的情况：插入引用用户的行时，外键检查给用户行加共享锁（等待重复的唯一键时也是），之后再改这个用户的积分就要升级为排他锁；`OnConflict().DoNothing()` 在 MySQL 上是 `ON DUPLICATE KEY UPDATE`。

## 决策
- **一个顺序**：会改积分或材质计数的事务，在任何其它写入之前，先锁材质（`texture.Lock`），再按用户 id 从小到大锁住所有会改到的用户（`score.Lock(ctx, tx, ids...)`）。两个事务就不会各自拿着一把锁、等对方的另一把。
  - 收藏、取消收藏：材质，然后收藏者与上传者。
  - 删除材质、改为私有（`lockWithClosets`）：材质，然后衣柜里有它的所有人与上传者。
  - 举报：提交时锁材质与举报人；处理时锁材质，然后举报人、同一材质其它待处理举报的举报人和删除会退款的所有人。别人刚处理过的其它举报跳过，不再让整次处理失败。
  - 建角色、上传材质：先锁用户再插入。管理员放入衣柜：先改材质计数再插入。
- **锁用的是无变化的更新**（`score = score + 0`、`likes = likes + 0`）：这个 ent 构建没有 `FOR UPDATE`，而行锁对三种数据库都有效。
- **MySQL 连接截断时间到微秒**（`timeTruncate=1µs`），与 PostgreSQL 一致，到期时间不受 MySQL 四舍五入影响。
- 不在事务里用 `DoNothing` 处理并发冲突；需要时先用条件更新"认领"一行（338ee51）。
- **每个新事务都要有并发测试**，并且要在 PostgreSQL 上跑（`dbtest.ForEach`）。MySQL 只在 CI 里跑，本地验证通过不代表 MySQL 通过。

## 备选方案
- 遇到死锁自动重试整个事务：掩盖问题、放大负载，而且已经发出的副作用（邮件、事件）不能重放。
- `SERIALIZABLE` 隔离级别：三种数据库的行为不同，冲突时同样要重试。

## 影响
- 新增 `score.Lock`、`texture.Lock`、`Service.UsersOf`；举报、收藏、取消收藏、删除材质、改可见性、放入衣柜、上传、建角色的事务改为先加锁。
- 新增并发测试：互相收藏、同一材质的多条举报同时处理、同一用户并发上传与建角色、多人同时收藏同一材质；前两个在修复前的代码上能在 PostgreSQL 复现死锁（40P01）。
- 删除很热门的材质时，会先逐个锁住所有收藏者，语句数随收藏数增长；删除本来就要逐个退款，量级不变。
