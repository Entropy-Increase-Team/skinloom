进入 M4 之前，对照 Blessing Skin 的源码和设计文档 01–06、ADR 0001–0026，把 SkinLoom 的架构和代码从头审查了一遍。对外协议（CSL、USM、Legacy、Yggdrasil、OAuth 与 `/api/*`）的路由和 BS 逐条对得上，整体方向没有要回退的地方。问题集中在并发：六个问题都用并发测试在 SQLite 和 PostgreSQL 上复现，然后一并修掉。

## 复现了什么

审查时临时写了几个并发测试，基于修复前的接口，复现后删除：

| 场景 | 修复前 |
|---|---|
| 同时发出几次"改为私有"（双击） | 6 个请求扣了 6 次差价 |
| 给角色穿上材质，同时把它移出衣柜 | 角色穿着不在衣柜里的材质（SQLite 150 轮 149 次） |
| 删除角色，同时把它穿着的材质移出衣柜 | PostgreSQL 60 轮 59 次死锁 |
| 删除上传者账号，同时有人收藏他的材质 | 死锁；收藏常因给已删除的上传者发奖励而报 500 |
| 两位管理员同时保存有重叠键的设置 | PostgreSQL 200 次保存 130 次死锁 |
| 同一时刻发出一批错误密码 | 200 个请求全部做了密码校验，限额是 10 |

前五个的根源相同：事务里的判断用的是事务开始前读到的数据；ADR 0026 的加锁顺序只覆盖改积分的事务，删角色、删用户、保存设置都不在里面。最后一个是"先检查、做完密码哈希再计数"，并发请求都在计数之前通过了检查。

## 怎么修的（ADR 0027）

- **加锁之后再判断**：材质先锁住再重读，可见性、上传者、类型都按锁里读到的值。穿戴和转移角色先锁住相关材质，再查衣柜。
- **加锁层级扩展**：材质 → 用户 → 角色 → 其它。删角色先锁主人。删用户的钩子挪进删号事务，先锁他的材质、再锁用户；期间账号被恢复时整个事务回滚，私有材质不会被提前删掉。
- **设置按键名顺序写入。**
- **限流一步完成**：`Limiter.Take` 检查和计数在同一把锁里，成功登录再撤回。所有"检查、做事、计数"的地方都换成了它。
- 顺带修的同类问题：删号时衣柜被外键删除，收藏数没减（BS C04 回来了）；删除材质时上传者自己角色的槽位由外键清空，`Last-Modified` 不变，`/{name}.json` 一直回 304；SQLite 的 DSN 带参数时外键被静默关闭。

## 补上的地基（ADR 0028）

- **领域事件**：Hook 总线原来只有 `settings.changed`。现在按设计文档 05 §4.4 的目录声明了用户、角色、材质、衣柜、举报五类共 15 个事件，在变更的事务里写进任务队列（outbox），提交后投递，至少一次。没有监听者时不写任何东西，所以现在零开销。Guard 和 Filter 随插件运行时一起做。
- **审计和变更同事务**：管理操作原来先调用服务、再在事务外写审计。现在服务直接接收审计记录，在自己的事务里写入。管理员同时改名和转移角色也合成了一个事务，原来可能只成功一半。

## 暂存代码复查

修完之后又把暂存的全部改动从头复查了一遍，逐个列出每个改动过的事务的加锁顺序。又找到三处问题，都先写测试、确认失败，再修：

- 处理举报仍是先读举报、再开事务。举报人在这期间被删除时，奖励会发给已删除的账号，返回 500。现在加锁之后重读。
- 删除材质时清空穿戴槽位用的是 `IN (所有角色 id)`，7 万个角色穿着的材质删不掉（SQLite 报 "too many SQL variables"）。现在按条件更新。
- 加锁覆盖不到删号的同一瞬间账号主人新收藏的那一条。补上设计文档里一直有、ADR 0019 推迟了的每日被收藏数校准。

两点记进 ADR 0028，留到上线插件之前处理：事件和邮件共用一个顺序执行的任务执行器；材质事件里有私有材质的 hash。

## 验证

- 每个问题都有对应的回归测试：并发改私有只扣一次、收藏与改私有并发、穿戴与移出衣柜并发、删角色与移出衣柜并发、删用户与收藏并发、并发保存设置、成批错误密码、删号钩子回滚、事件只在提交后存在、SQLite DSN、举报人已被删除、7 万个角色穿着的材质、被收藏数校准。在 SQLite 和 PostgreSQL 上全部通过，并发测试在 PostgreSQL 上用 `-count=10` 重复。
- `go vet`、完整的 `go test ./...`（SQLite + PostgreSQL）、前端类型检查与单测。
- 用 `skinloom serve` 起了真实服务，走了登录爆破、改私有、穿戴、删号等流程。
