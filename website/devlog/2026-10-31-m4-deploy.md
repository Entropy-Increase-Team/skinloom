M4 最后一部分：`skinloom service install` 一条命令注册为系统服务；Kubernetes 可以用 Helm 安装；每种部署方式在 CI 里都会按文档从零部署一遍。

## 系统服务（ADR 0033）

以前发行包带一个 `service/` 目录，里面是手写的 systemd 单元、launchd plist 和 Windows 计划任务脚本，用之前要自己改路径。Windows 上那其实是计划任务，不是服务。

现在由程序自己注册（用 kardianos/service）：

- `skinloom service install`，然后 `start`。另有 `stop`、`restart`、`status`、`uninstall`。
- Linux 生成 systemd 单元，保留了原来的全部沙箱选项：系统目录只读，只能写 `data/` 和前端缓存。默认以 `skinloom` 用户运行，安装时把 `data/` 交给它。
- macOS 是 `/Library/LaunchDaemons` 下的守护进程，开机运行，不用登录。
- Windows 是真正的服务，以 LOCAL SERVICE 运行，延迟自动启动，失败后 5 秒重启。安装时用 icacls 只给它 `data\` 和前端缓存的写权限。
- 没有管理员权限时直接失败，并提示用管理员终端或 sudo。权限设置失败时把刚注册的服务删掉，不留半装的状态。
- 站点自己退出（比如配置写错）时进程也退出，交给服务管理器重启，不会出现"服务在运行、网站却打不开"。

服务的控制台没人看，首次启动的一次性安装链接会丢，所以加了 `log.file`：以服务运行时默认把日志写到 `data/logs/skinloom.log`，超过 20 MB 时在启动时轮换一份。Windows 服务的标准错误可能是无效句柄，所以先写文件、再尽力写控制台；`io.MultiWriter` 遇到第一个错误就会停，不能直接用。

## `/readyz` 等前端

用发行包测试时发现，启动后约一秒内 `/readyz` 已经返回 200，首页却是 502：前端子进程还在启动。现在前端由本进程启动时（managed / dev），`/readyz` 还要能连上前端端口才算就绪。前后端分离部署时前端有自己的探针，后端不管。

## Helm Chart

`deploy/helm/skinloom`：

- `mode: allInOne`（默认）：单 Pod、SQLite、5 Gi 数据卷，和 `skinloom` 镜像一样。
- `mode: split`：后端加前端，前端可以多副本，带 PDB，可开 HPA。
- 外部数据库的 DSN 从已有的 Secret 读取，不写进 values。
- 另有 Ingress、可信代理、`server.extraEnv`（比如 S3 配置）、资源与调度。卸载 Chart 时保留数据卷。
- 安全设置和 Kustomize 清单一致：非 root、只读根文件系统（split 模式的后端）、去掉全部 capabilities、seccomp、不挂载 ServiceAccount 令牌。

互相矛盾的参数在安装时就报错并说明原因，而不是装上之后才出问题：SQLite 配多个后端副本、多副本用 ReadWriteOnce 卷、allInOne 想扩容、外部数据库没给 Secret。不需要迁移 Job，后端启动时带锁执行迁移。Kustomize 清单保留，给不想装 Helm 的人用。

## 部署冒烟测试

以前 CI 只检查部署文件的语法，从来没真正启动过。`deploy/smoke/smoke.sh` 像新站长一样走一遍：

1. 等待就绪，检查首页能渲染。
2. 从日志里找出安装链接，完成安装。
3. 登录，创建角色。
4. 用 CustomSkinLoader 接口取回这个角色，不存在的角色返回 404。
5. 后台的系统状态里没有错误。

新工作流 `deploy-smoke.yml` 对每种部署方式都跑这个脚本，镜像全部从当前提交构建：

- Compose 的 minimal、standard、postgres 三个变体。
- 在 kind 集群里用 Helm 安装：allInOne + SQLite，split + PostgreSQL。
- Linux 发行包：先按文档前台启动，再用 `skinloom service install` 注册为 systemd 服务，确认状态是 running，冒烟测试通过后停止并卸载。

原来的部署文件检查也加上了 Helm：lint、几组参数的渲染、kubeconform 校验，以及非法参数确实会被拒绝。

顺带修了一个打包问题：在没有 `zip` 的 Windows 上，发行包由 PowerShell 的 `Compress-Archive` 压缩，路径分隔符是 `\`，`unzip` 会警告，macOS 会解压出错。现在改用 Windows 10 起自带的 `tar.exe`。

## 验证

- 新测试：生成的 systemd 单元（带空格的路径会加引号）、服务命令行、拒绝安装 `go run` 产生的临时程序、日志轮换、控制台写失败时日志文件照常写入、`/readyz` 等前端。
- `go fmt`、`go vet`（Windows、Linux），macOS 交叉编译；完整的 `go test ./...`（SQLite 与 PostgreSQL）。
- Helm：lint 与多组参数渲染通过，矛盾的参数都被拒绝。
- 在本机用当前代码打出 Windows 发行包，解压到空目录，按文档启动，用和 `smoke.sh` 相同的步骤走完一遍，日志里没有警告。
- 普通权限下执行 `skinloom service install`，按预期失败并提示用管理员终端；`service status` 显示 not installed。

## 仍未验证

- Compose、Helm 和 systemd 服务的从零部署只在新的 CI 工作流里跑，本机不运行 Docker，需要推送后看结果。
- 真实的 Windows 服务与 macOS launchd 安装还没跑过（CI 只覆盖 systemd），需要在有管理员权限的机器上手动验证一次。
- kubeconform 只在 CI 里跑。
