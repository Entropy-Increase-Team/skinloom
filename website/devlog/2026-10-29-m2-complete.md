M2 第五部分补上了材质与角色里程碑的最后几块：服务端画头像和预览图、站内通知与公告、S3 兼容的对象存储。到这里，路线图里 M2 的每一项都已经可用，下一站是 M3 的外置登录。

## 本期完成

- **渲染器**（`internal/render`）：
  - 2D 与立体 3D 头像，皮肤正背面预览，披风预览。
  - 旧版 64×32 皮肤按 Minecraft 的方式补出左手左腿；整块不透明的旧帽子层视为空。
  - 最近邻取样，像素清晰；默认无损 WebP（纯 Go 编码器），也可以要 PNG。
  - 尺寸取固定档位，结果按"文件哈希 + 参数"缓存在内存（LRU、同键只画一次、最多 4 个同时画），这个键也是 `ETag`。
  - 私有材质的响应标记为 `private`，CDN 不会缓存。
- **头像**：衣柜里"设为头像"，页头和个人资料页显示。材质被删或变成别人的私有材质时自动退回占位头像。
- **站内通知**（`internal/notify`）：
  - 群发只写一条公告，用户打开收件箱时才复制自己的一份，唯一索引保证并发也只有一份。
  - 铃铛未读数、收件箱、点开即已读、全部已读、后台发送表单。
  - Markdown 在服务端渲染（goldmark 安全模式）；站点公告也改成 Markdown 显示。
- **S3 兼容存储**（minio-go）：
  - 本地存储之外的第二个驱动。
  - 重复上传同一张图时，"刷新修改时间"用对象自我复制实现，延迟清理照常工作。
  - 可配 `public_url` 让 CDN 直接发文件。
- **链接预览**：公开材质页带 `og:image`。
- 设计记录：[ADR 0021 渲染器、站内通知与 S3 兼容存储](https://github.com/Entropy-Increase-Team/skinloom/blob/main/docs/adr/0021-renderer-notifications-and-s3.md)。

## 差点出的事故

`users` 要加两列，Atlas 为 SQLite 生成的迁移是"重建整张表"：关外键、建新表、拷贝、`DROP TABLE users`、改名。

问题在于 goose 把每个迁移文件放进事务里执行，关外键的 PRAGMA 在事务里不起作用，而 SkinLoom 的 SQLite 连接开着外键。于是 `DROP TABLE users` 会先删光所有用户，并顺着外键把会话、衣柜、角色、积分流水一起删掉：已有站点升级时会丢掉几乎所有数据。

处理：
- 这次手写成 `ADD COLUMN`；
- 头像字段不设外键（加外键列在 SQLite 上只能重建）；
- 新增一个测试，任何 SQLite 迁移再出现重建表就失败。

## 本地实测（`skinloom up --dev`）

1. 上传几张皮肤（经典、纤细、披风、私有）。通过服务器取 PNG：
   - 立体头像能看到脸、眼睛、刘海和帽子层的一条黄带，顶部是头发，右侧是较暗的侧脸；
   - 预览图左边正面、右边背面，手臂位置左右互换，背面是后脑勺的头发。
2. 响应检查：
   - 默认请求返回 `image/webp`，披风的头像 422；
   - 匿名访问私有材质的预览 403，上传者访问 200 且 `Cache-Control: private, no-cache`。
3. 公开材质页的 HTML 里有 `og:image`，地址是完整的预览图 URL；私有材质页没有。首页公告的加粗、列表、链接都渲染出来了，混在里面的 `<script>` 被去掉。
4. 管理员群发一条维护公告，再单独给 alice 发一条。alice 登录：
   - 铃铛显示 2；
   - 收件箱里单发的那条在上，公告带"公告"标记，展开是渲染好的 Markdown。
5. 点开一条后，列表显示"1 条未读"，但铃铛还是 2。这里发现铃铛只在切换页面时重新计数，改成收件箱已读后通知铃铛，再试铃铛立刻更新。
6. alice 在衣柜给皮肤点"设为头像"：页头头像立即换成这张皮肤（地址里带版本号，不被缓存挡住），个人资料页显示 2D 与立体头像和"移除头像"。
7. 管理员在概览页用表单按邮箱给 bob 发通知，bob 收件箱里有这条单发通知加那条公告，共 2 条未读。服务端日志没有警告。

S3 驱动用测试里的假 S3 验证（上传、重复上传刷新时间、Range 读取、列举、删除、公开地址、桶不存在时启动报错），没有接真实的云存储。

## 测试

- 渲染：
  - 尺寸取档；旧皮肤镜像与帽子层规则；
  - 2D/3D 头像的各个面与透明角，含 2 倍分辨率皮肤；
  - 预览图尺寸、背面、纤细手臂、披风；
  - WebP 无损往返解码；缓存只画一次、按字节淘汰、错误不缓存。
- 通知：收件箱、已读、他人的通知 404、公告受众与"之后注册的收不到"、十个并发投递只有一份、Markdown 安全（脚本、`javascript:` 链接、`onerror`）。
- 头像：披风、别人的私有皮肤、变私有后对他人隐藏、删除材质后清空。
- S3：上面列的全部行为，以及缺少字段、地址带协议、CDN 地址不完整时的配置校验。
- HTTP：
  - 各个渲染地址的格式、尺寸、`immutable`、304、422、403、404、占位图；
  - 私有响应的 `Cache-Control`；
  - 通知全流程、站点公告 HTML、审计。
- 迁移：SQLite 不重建表的守卫测试。
- 全量回归：
  - Go：`go test ./...`（含 PostgreSQL 18）、vet、staticcheck、govulncheck；
  - 生成代码无差异、迁移无漂移；
  - 前端：类型检查、单元测试、生产构建、`bun audit`。

## 问题与风险

- 渲染结果只在内存里缓存，重启或多实例时会各自重画；渲染一次只要几毫秒，暂不需要持久化。
- S3 驱动没有在真实云服务上跑过，第一位用对象存储的站长请留意启动日志。
- `golang.org/x/crypto` 有一条暂无修复版本的公告，代码没有调用到受影响的部分。
